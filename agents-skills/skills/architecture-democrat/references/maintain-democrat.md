# Procedure 3, democrat - the implementer may propose

The channel to propose second. The implementer sends a proposed rule along with the question, and the architect weighs it.

**Read `architect`'s procedure 3 before this file.** Its steps, its derivability test and its five ruling statements hold in both modes, and everything below is only what having a proposal in hand changes.

**Treat a proposal as evidence, never as a decision.** The implementer holds the code and the architect holds the contract; a proposal carries information across that line and carries no authority with it.

## What a proposal must carry to be weighed at all

**Send back a proposal missing any of the three fields below, unweighed.** Asking for the missing field costs one round, while weighing an incomplete one cannot tell a rule from a preference.

| Field | What it must say |
|---|---|
| the case | the situation the contract does not settle, stated without reference to the branch |
| the rule | the rule proposed, in the form `architecture-md` §4 requires of any rule |
| the extension | at least one file besides the one in hand that this rule would place, and where it puts it |

**Reject a proposal whose rule places only the file that raised it.** That is an exception dressed as a rule: the contract grows by a clause binding nothing else, and the next file of the same kind arrives as a fresh question.

**Refuse a proposal that reaches any of `architecture-md` §4's laundering moves, however well it argues.** Merit is not the test: the move is judged by the order of reasoning, and this mode is where a good argument arrives already wrapped around one.

## How much of the branch the architect may read

**Read the proposal and the one file it was raised about; open nothing else in the branch.** That file is the mode's entire extra allowance, and everything past it is the branch teaching you the shape you are meant to be judging.

**Name in the ruling every fact you took from the proposal.** Reading cannot be undone, so visibility is the guard left: the user deciding whether this mode still works has to see which half of the ruling the implementer supplied.

## How a proposal is weighed

**Ask what the rule would be if the branch did not exist, and rule that.** This is the test that survives a good argument, because a proposal persuades by how well it fits what is already written, and this question cannot see that fit.

**Weigh the rule against the contract and the product, never against what the alternative costs the proposer.** Rework is the price of having been wrong, not an argument about where a boundary belongs, and it is the one cost the thread makes visible.

## What an accepted proposal becomes

**Issue the ruling in your own words and on your own authority, never as the proposer's text merged in.** A contract written in two voices cannot be read for which rules were weighed and which were pasted.

**Hand the proposal's original form to the log's owner wherever the ruling narrowed it.** The shared step hands the alternatives a ruling rejected to the log's owner, and here the nearest alternative is the version the implementer asked for.

## What a rejected proposal is owed

**Name the contract term the proposal collided with, not the verdict.** A rejection carrying only the outcome teaches the implementer to argue harder; one naming the edge or the invariant teaches them what a weighable proposal looks like.

**Settle the underlying question in the same reply that rejects the proposal.** The implementer is still blocked, and a refusal alone is slower than autocrat while costing more.

**Settle a case the contract already carries by naming the section that carries it, and every other one by ruling it.** Only the second is a decision, and only a decision reaches the log.

**Put a rule back as a counter-proposal wherever the case was derivable and the aim was sound.** This mode holds the proposer's reasoning, so it can name what the contract implies and ask whether that was the ask; autocrat holds only the question.

## When to tell the user this project belongs on maintain autocrat

**Tell the user to switch to maintain autocrat once any row below has shown twice.** One bad proposal is noise, a repeat is the mode failing, and only the user who chose democrat can change it.

| Pattern, seen twice | What it says |
|---|---|
| proposals that place only the branch in hand | the implementer is tuning the file rather than the contract |
| a ruling nobody could tell apart from the proposal that prompted it | the weighing is a rubber stamp |
| the same rule re-proposed after a reasoned rejection | the channel is being used to relitigate rather than to inform |
| a proposal whose rule is right and whose stated reason is the code | the reasoning order `architecture-md` §4 forbids, arriving pre-argued |
| a proposal on a case the contract already carries | the proposer is querying the contract rather than reading it, and the counter-proposal channel is absorbing the cost |
