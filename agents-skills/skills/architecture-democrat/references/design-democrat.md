# Procedure 1, democrat - the tree may contest the draft

The code works and the user is not entirely satisfied with the shape it has; they want the shape it should have, argued against the one in the tree rather than drawn on a green field.

**Produce a draft that owes the tree nothing, then let the tree contest it.** The contest is the whole of this mode; a tree read first becomes the template, and there is then no draft left for it to contest.

## What is settled before a source file is opened

1. **Read the product docs and nothing under the source root.** What the product does, and what it must survive - a provider change, a second surface, data outliving the code.
2. **Get both from the user where the repo carries no product docs, before drafting anything.** The tree does not answer them, and a tree opened to fill the gap has just become the draft.
3. **Draft the decomposition whole from best practice for this class of product: dependency direction, the outside edge behind ports, where the value stays testable.** A half-draft is finished from what is in context, which by then is the tree.
4. **Write that draft down and change nothing in it for the rest of the mode.** `architecture-md` §4 judges laundering by the order of reasoning, and a draft kept only in your head leaves no record of what that order was.

## What the tree is opened for

**Open the tree through one question: which roles genuinely exist, and which of them has proven something.** Everything else it offers - file counts, today's import graph, the directory layout - is procedure 4's input, not this file's.

**Collect what the tree offers as claims against the draft, never as edits to it.** A claim is a proposed bend plus its argument, and an edit made while reading is a bend nobody recorded.

## What discharges the burden of proof, and what only asserts

**Accept a bend only on evidence from outside the tree.** The tree's shape is never evidence for the tree's shape: it is the claim under test, so reading it as proof closes the question with itself.

**Never construct the tree's argument on its behalf.** The burden is the tree's, so an argument you supply for it is the draft losing to a case nobody made, and a claim nobody can argue is simply refused.

| The tree's argument | Verdict |
|---|---|
| a failed attempt to do it the draft's way, whose reason still holds | evidence, and the strongest - the draft's shape ran here and lost. Check the reason is structural, not a deadline or a since-fixed library version |
| a recorded blast radius from when the boundary was crossed - an incident, a revert, a defect the seam let through | evidence - the crossing was tried and its cost is on record |
| a platform rule that makes the draft's shape unbuildable here | evidence about the runtime, which binds a rewrite from scratch just as hard |
| longevity, it has stood for years | habit - age records that nothing challenged it, which is the experiment missing rather than its result |
| uniformity, every module already does it this way | habit - uniformity is what copying produces, so it counts copies rather than reasons |
| migration cost, too many files would have to move | not about shape at all; it orders the migration, and the file still states the target |
| the author's confidence that it works | assertion - "it already works this way" with a person attached |

**Verify a claimed incident, revert or failed attempt at its source before it counts.** An argument of an evidence kind is still an assertion until the commit, the log entry or the postmortem is in hand.

**Send a claim the tree loses to procedure 4, never back into the draft.** A refused claim is drift, and drift is reported against the contract rather than absorbed into it.

## How a proven bend is told from a laundered one afterwards

**Diff the frozen draft against the finished file and treat every difference as a bend owing a reason.** Inside the finished file the two are indistinguishable, so the draft is the only surviving record of which came first.

**Write a bend's reason as a sentence about the product before accepting the bend.** A reason writable only as a sentence about the repo is the laundering spelled out, and it is the one difference that survives into the finished file.

**Ask what would have to change for the bend to be wrong, and refuse it where the only answer is the code.** A rule whose sole falsifier is the tree's present arrangement is that arrangement restated as a rule.

**Walk `architecture-md` §4's laundering moves against that diff rather than against the draft.** Each move is a bend that already happened, so the checklist has nothing to check until the diff exists.

## Where this mode hands off

**Carry the frozen draft, the accepted bends and their reasons into `architect`'s four shared steps.** The reconciliation is finished before the first coverage question, and those reasons are what the body-assembly step writes down.

**Report the bend count and the refused claims with the deliverable.** A draft that bent everywhere did not survive the contest, and nothing in the finished file shows that the contest ever happened.
